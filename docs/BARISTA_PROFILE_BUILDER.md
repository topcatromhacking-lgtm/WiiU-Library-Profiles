# v0.3: Offline Barista profile builder, verified foundations

## Current status (2026-10-11)

The user's historical two 130,116-byte `BaristaAccountSaveFile.dat` samples were inspected **locally**, along with a 550-row Excel list and the 511-game hardware MCP/ACP metadata catalog. No raw private game inventory, binary Barista saves or Excel contents should be committed to this repository.

A standalone **offline-only** standard-library Python prototype is packaged privately for the user (not yet published as a repo release). It performs:
- Source-file audit and SHA-256 fingerprinting;
- Snapshot exact per-slot game order into editable JSON;
- Regenerate each historical Barista using its own matching binary template and snapshot, byte-for-byte identical;
- Reject input templates with a different SHA-256 from the profile plan;
- Reject missing/non-game Title IDs using the current installed MCP/ACP catalog;
- Protect system and homebrew slots and preserve the entire unknown post-bank data unchanged.

## Grounded binary findings

Both observed binary saves consist of:
- 300 x 16-byte NAND-side records at `0x0000..0x12BF`;
- 300 x 16-byte USB-side records at `0x12C0..0x257F`;
- Opaque remaining Barista data from `0x2580` onward.

These are **300 paired positions**, not 600 distinct Menu icons. The specific historical templates contained 283 and 285 USB game records, respectively. Protected NAND/system/homebrew entries numbered 17 and 15. Together, the templates contained 506 unique current games, 62 shared games, and lacked only the five games used in the v0.2 experiment. The Excel table contained 550 rows, representing 511 distinct IDs with 39 duplicate TurboGrafx listings. One The Wonderful 101 ID in Excel is stale relative to the current console inventory.

The prototype's **no-op rebuilding reproduced BOTH entire 130,116-byte original files byte-for-byte** (including the opaque section). A simulated two-game swap altered only the corresponding USB slot records. The obsolete Excel Title ID was rejected by the installed-title check.

## Critical limits

- No-op binary fidelity does **not** validate new layouts on physical hardware.
- A Barista save persists icon positions while the MCP title list enumerates available records. Future profile switching must coordinate these two layers.
- No hot-swapping or direct edits to live NAND, USB, `titlesmap`, or redirected Barista saves.
- The `Homebrew on Wii U Menu` plugin redirects the user Menu save to an SD copy. Every future write must be prepared as an offline copy, hashed, backed up and applied with the Menu not running.
- Generated layouts must preserve all protected fixed entries and stay within the hardware-tested 300-position layout structure.
- Once safe switching is validated, compare a generated third profile against the user's historical 1 and 2. Then integrate with the Menu-scoped view-filter logic if required.

## Validation ladder

1. **Complete:** exact original-to-generated byte-for-byte roundtrip for both files.
2. **Complete:** slot-only synthetic edits preserve NAND-side and opaque data.
3. **Complete:** catalog check rejects a stale game Title ID.
4. **Next:** move portable, **generic-only** offline code into this branch with synthetic fixtures and tests; keep personal JSON/private binaries local.
5. **Next:** generate profile 3 offline, derived from user-approved category selection and the known-good templates.
6. **Later hardware gate:** safely switch to a prepared layout while the Wii U Menu is not running and verify persistence, restoration, folder behavior, Homebrew entries and no unintended save changes.
